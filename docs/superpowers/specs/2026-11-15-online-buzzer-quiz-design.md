# オンライン早押しクイズ 設計書

日付: 2026-11-15
状態: 承認待ち

凡例: 【決定】は依頼者が決めたこと。【提案】は設計者の判断で、依頼者が変更できる。

## 1. 目的

学校の授業やクラス活動で、生徒が各自の端末からオンラインで参加し、早押しクイズを遊べるようにする。
進行(出題・早押し判定・採点・問題送り)はアプリが自動で行う。

## 2. ゴール・対象外・避けたいこと

### ゴール
- 【決定】オンラインで参加する早押しクイズであること。
- 【決定】アプリが自動で進行し、解答は4択であること。
- 【決定】学校で使う。ルームは1つだけでよい。
- 【決定】サーバーは Cloudflare を使う。
- 【決定】サーバーの管理画面で問題を作れる。
- 【決定】問題をセットとして保存でき、セットを選んで出題できる。
- 【決定】端末は Android。Android Studio のエミュレーター上で表示・動作確認する。
- 【提案】アプリを開いて名前を入れるだけで参加できる(ログイン不要)。
- 【提案】1クラス、同時40人程度まで快適に動く。
- 【提案】早押しの順番はサーバーに届いた順で決まり、同時押しでも解答権は必ず1人だけになる。

### 対象外(今回は作らない)
- 問題の一括取り込み・書き出し(CSV など)、画像や音声つきの問題、セットの複製、1つの問題を複数のセットで共有すること、複数セットを混ぜた出題。
- Android アプリ内での問題作成(問題作成はサーバーの管理画面だけで行う)。
- 複数ルーム、合言葉、アカウント登録・ログイン。
- 成績の長期保存、過去の結果の閲覧。
- 効果音・BGM。
- ストアでの配布、実機への配布方法の整備。
- Android 以外(Web / iOS / デスクトップ)での検証。コードは Flutter なので動く見込みだが、保証しない。開発中に2人目の参加者として Chrome や Windows 版を起動して使うことはある。

### 避けたいこと
- 先生の端末が切れただけでゲームが止まること。
- 通信の速い・遅いではなくバグで解答権が2人に渡ること。
- 生徒が参加するまでに手順が多く、授業時間を使ってしまうこと。

## 3. 制約

- 既存プロジェクト `quiz_new`(Flutter 3.41.9 / Dart SDK ^3.11.5 のひな形、依存パッケージなし)の上に作る。
- 開発機は Windows 11。Node.js 22 / npm 11 / git あり。wrangler は未導入(サーバー用ディレクトリの devDependency として入れる)。
- Cloudflare は無料プランに収まる構成にする。Durable Objects は SQLite バックエンド(無料プランで使える方式)で宣言する。
- 画面の文言はすべて日本語。
- Android エミュレーター(スマホ縦向き)で動くこと。先生画面はタブレットや横向きでも崩れないこと。

## 4. 検討した作り方

| 案 | 内容 | 良い点 | 弱い点 |
|---|---|---|---|
| A. Firebase | ルーム状態を Firebase に置き全端末が購読 | 自前サーバー不要 | 無料枠ではサーバー側処理が使えず、先生の端末が進行役になる(切れると止まる) |
| B. 先生のPCをサーバーに | 校内 Wi-Fi 内で完結 | 外部サービス不要 | 学校 Wi-Fi は端末間通信を遮断していることが多い。毎回起動が必要 |
| C. Cloudflare Workers + Durable Objects | ルーム1つを Durable Object 1個が持ち、全端末が WebSocket 接続 | 進行も判定もサーバーが行う。ルーム1つの条件に合う | サーバー側は TypeScript で書く |

【決定】C。依頼者が Cloudflare のアカウントを持っており、Cloudflare で進めると指定した。
進行をサーバーが担えるので「先生の端末が切れても止まらない」を満たせる点でも A より合う。

## 5. 全体構成

```
生徒・先生の Android アプリ (Flutter)
        │  WebSocket で常時接続
        ▼
Cloudflare Worker ──── /ws ───▶ Durable Object「QuizRoom」(1個だけ)
                                   └ 参加者・問題・得点・タイマーを保持し進行
先生の PC のブラウザ ── /admin ──▶ 問題の管理画面(同じ Worker が返す)
```

- リポジトリ構成
  - `lib/` … Flutter アプリ
  - `server/` … Cloudflare Worker(TypeScript)。`wrangler.jsonc`、`src/`、`test/`
  - `docs/` … 設計書・計画書
- Worker は1つ。`/ws` への WebSocket 接続を固定名(例 `"main"`)の Durable Object に渡す。`/admin` は問題の管理画面(HTML)、`/api/...` はその管理画面が使う API。それ以外のパスは 404 を返す。サーバーの公開は `wrangler deploy` 1回で完了する。
- ゲームのルール処理は、WebSocket や Cloudflare の API に依存しない純粋な状態機械(入力: イベントと現在時刻、出力: 新しい状態と送信メッセージ)として分離する。これを単体テストの対象にする。
- フェーズの時間切れは Durable Object のアラームで起こす(接続が全部切れてもゲームは進み、終了まで行く)。
- ゲーム状態は Durable Object のストレージにも保存し、Durable Object が再起動しても続きから再開できるようにする。

## 6. 役割と画面

### 役割
- **生徒**: 名前を入れて参加し、早押しして解答する。
- **先生**: 【提案】トップ画面の「先生用」から暗証番号を入れて入る。ゲームの開始・中止・リセットを行う。解答はしない。先生画面は教室のプロジェクターに映す想定で、問題・解答者・全員の順位を大きく表示する。
  - 暗証番号は Worker のシークレット `HOST_PIN` で設定する。ローカル開発では `.dev.vars` に置く。未設定の場合、先生としての接続は拒否する。
  - 先生は同時に複数接続してもよい(PC とタブレットなど)。先生が0人でもゲームは止まらない。

### 画面
1. **トップ(参加)**: アプリ名、名前入力、「参加する」ボタン、小さく「先生用」リンク。
2. **先生ログイン**: 暗証番号入力。
3. **待機**: 参加者の名前一覧と人数。生徒には「先生が開始するまでお待ちください」。先生には問題セットの選択(セット名と問題数の一覧から1つ選ぶ)と「開始」ボタン。
4. **出題**: 問題番号、残り時間、1文字ずつ出る問題文、大きな「早押し!」ボタン、得点。
5. **解答**: 解答権を得た生徒にだけ4択ボタンと残り時間。他の人と先生には「○○さんが解答中」。
6. **問題の結果**: 正解の選択肢と、正解者名(または「正解者なし」)。数秒後に自動で次へ。
7. **最終結果**: 順位表。先生には「もう一度」ボタン(待機に戻る)。

出題画面(生徒)のイメージ:

```
┌──────────────────────┐
│ 第3問 / 10     残り 12秒 │
│                          │
│ 日本で一番高い山は富士山 │
│ ですが、二番目に…        │
│                          │
│      ┌──────────┐      │
│      │  早押し！  │      │
│      └──────────┘      │
│ あなた 2点 (3位 / 32人)  │
│ 1位 たろう 4  2位 はなこ 3│
└──────────────────────┘
```

- 【提案】40人では全員の得点を並べられないので、生徒画面は「自分の得点と順位」と上位3人を表示する。先生画面は全員を表示する。

## 7. ゲームのルール

【提案】このセクションの数値はすべて設計者の提案。サーバーの設定値1か所にまとめ、変えやすくする。

| 項目 | 値 |
|---|---|
| 1ゲームの問題数 | 最大10問(選んだセットからランダムに選び、ランダムな順で出す。同じゲーム内で重複なし。セットが10問未満なら全問) |
| 問題文の表示速度 | 1文字あたり 120ミリ秒 |
| 早押し受付時間 | 問題文が全部出てからさらに 10秒 |
| 解答の制限時間 | 10秒 |
| 問題の結果の表示時間 | 4秒 |
| 得点 | 正解 +1点、不正解 −1点(【決定】)。解答権を取って時間切れ・切断した場合も −1点。得点はマイナスにもなる。誰も押さずに時間切れになった場合は増減なし |

### フェーズの流れ

```
待機 ──開始──▶ 出題(文字が出る・早押し受付)
                 │ 誰かが押す              │ 受付時間切れ
                 ▼                          ▼
               解答(その人だけ4択)       問題の結果
                 │正解        │不正解/時間切れ
                 ▼            ▼
             問題の結果    まだ押せる人がいる → 出題に戻る(続きから)
                 │         全員お休み       → 問題の結果
                 ▼
        次の問題へ / 10問終わったら 最終結果 ──もう一度──▶ 待機
```

### 詳細
- **早押し**: 出題フェーズ中、サーバーに最初に届いた「押した」1件だけが有効。以降はフェーズが変わっているので無視される。その問題でお休み中の生徒の「押した」も無視する。
- **文字表示の一時停止**: 誰かが押した時点で、全員の画面で問題文の表示が止まる。サーバーが自分の時計から「何文字目まで出たか」を計算して全員に送り、全端末をその位置にそろえる。不正解で出題に戻ったときは、その位置から表示を再開し、残りの受付時間も止めたところから再開する。
- **4択**: 選択肢は解答権を得た生徒にだけ送る(他の生徒には送らない)。並び順は問題ごとにサーバーがシャッフルし、その問題の間は同じ順を使う。
- **不正解**: その生徒はその問題の間だけお休み。他の人には「不正解」とだけ伝え、どれを選んだかは見せない(残りの人が有利になりすぎないため)。
- **問題の結果**: 正解の選択肢を全員に表示する。
- **順位**: 得点の多い順。同点は同順位(1位、1位、3位…の付け方)。
- **途中参加**: ゲーム中でも参加できる。0点で、次の出題フェーズから早押しできる。
- **切断と再接続**: 端末ごとの参加者IDを端末内に保存する。再接続すると同じ名前・得点で復帰する。切断中の生徒は一覧で薄く表示し、得点は残す。解答権を持ったまま切断した場合は、解答の制限時間切れとして扱う。
- **名前**: 1〜12文字。前後の空白は取り除く。接続中の他の参加者と同じ名前は不可(エラーを表示して入力し直してもらう)。
- **先生の操作**: 「開始」(待機中のみ、参加者が1人以上、問題が1問以上あるセットを選んでいること)、「中止」(ゲーム中いつでも。待機に戻り得点は0に戻る。参加者は残る)、「もう一度」(最終結果から待機へ。得点は0に戻る)、「全員を退出させる」(待機中のみ。次のクラスに入れ替えるため。参加者一覧を空にする)、「1人を退出させる」(いつでも。先生画面の参加者一覧から選ぶ。ふざけた名前や、別の端末で入り直して残った名前を消すため。退出させられた端末はトップ画面に戻り、入り直すことはできる。解答中の生徒を退出させた場合は解答の時間切れと同じ扱い)。

## 8. 通信

- 接続先: ビルド時の `--dart-define=SERVER_URL=...` で指定する。指定がないときの既定値は `ws://10.0.2.2:8787/ws`(Android エミュレーターから開発機上の `wrangler dev` に届くアドレス)。公開後は `wss://<worker名>.<アカウント>.workers.dev/ws` を指定してビルドする。
- Android の設定: `AndroidManifest.xml` に `INTERNET` 権限を追加する。`ws://`(暗号化なし)での接続はデバッグビルドでのみ許可し、リリースビルドは `wss://` のみとする。
- 形式: JSON テキスト。すべてのメッセージに `type` を持たせる。
- クライアント → サーバー(意味):
  - `join`(生徒として参加: 参加者ID、名前)
  - `host_login`(先生として入る: 暗証番号)
  - `buzz`(早押し)
  - `answer`(選択肢の番号)
  - `host_start`(出題するセットのIDを持つ)/ `host_abort` / `host_again` / `host_clear` / `host_kick`(先生の操作。`host_kick` は対象の参加者IDを持つ)
- サーバー → クライアント(意味):
  - `state`(現在のフェーズ、問題番号、問題文、表示済み文字数と表示が動いているか、各締切までの残りミリ秒、参加者一覧と得点、解答中の人、自分がお休みかどうか)。フェーズが変わるたび、および参加者に変化があるたびに全員へ送る。接続直後にも送るので、途中参加や再接続でも画面が復元できる。
  - `choices`(解答権を得た本人にだけ: 4つの選択肢)
  - `sets`(先生にだけ: セットのID・名前・問題数の一覧。先生の接続時と、管理画面でセットや問題が変わったときに送る)
  - `error`(名前の重複、暗証番号違いなど。日本語の文言を含む)
- 時刻は端末の時計に頼らない。サーバーは「残りミリ秒」を送り、端末は受信時点からのカウントダウンで表示する。
- 切断時、クライアントは間隔をあけながら自動で再接続する。再接続中は画面上部に「再接続中…」を表示する。
- 【提案】不正対策は「選択肢を解答者以外に送らない」「正解番号は結果フェーズまで送らない」まで。問題文の全文は出題開始時に端末へ届く(通信をのぞけば先読みできる)が、学校利用では許容する。

## 9. 問題セットと管理画面

### 問題セット
- 【決定】問題をセットとして保存でき、先生がセットを選んで出題できること。
- 【提案】以下の決まりは設計者の提案。
- セットは「ID、名前、作成日時」を持つ。問題は必ず1つのセットに属し、「ID、所属セット、問題文、選択肢4つ、正解の位置、セット内の並び順」を持つ。
- 1つのゲームで使うセットは1つ。先生が待機画面で選ぶ。前回選んだセットを次回の初期選択にする。
- 出題は、選んだセットからランダムに最大10問、ランダムな順で行う。10問未満のセットは全問を出す。
- 問題が0問のセットは選択肢に表示するが選べない(「0問」と表示)。セットが1つもない、または全部0問のときは開始できず、先生画面に「管理画面で問題を登録してください」と表示する。
- ゲーム開始時に、出題分の問題をゲーム状態に写し取る。ゲーム中に管理画面でセットや問題を変更・削除しても、進行中のゲームには影響しない。

### 保存場所
- 【提案】セットと問題は QuizRoom の Durable Object のストレージ(SQLite)に保存する。ルームが1つでデータ量も少ないので、別のデータベース(D1 など)は使わない。

### 最初から入っているセット
- 【提案】初回起動時(セットが1件も保存されたことがないとき)に、セット「サンプル(一般常識)」を30問つきで自動登録する。対象は小学校高学年〜中学生の一般常識(地理・歴史・理科・国語・算数/数学・生活)。
- サンプルの作成は今回の実装作業に含む(作り手が書く)。問題文は早押し向きに、後半で答えが絞れる書き方にする(例:「日本で一番高い山は富士山ですが、二番目に高い山は何でしょう?」)。誤答はもっともらしいものにし、事実関係を確認する。
- サンプルは管理画面から編集・削除できる。削除しても自動では復活しない。

### 管理画面
- 【決定】サーバーの管理画面で問題を作れること。
- 【提案】以下はすべて設計者の提案。
- 場所: Worker の `/admin`。PC のブラウザで開く(開発中は `http://localhost:8787/admin`、公開後は `https://<worker名>.<アカウント>.workers.dev/admin`)。
- 作り: Flutter ではなく、Worker が返す1枚の HTML(素の HTML / CSS / JavaScript。ビルド工程や外部ライブラリなし)。文言は日本語。
- 入り方: 先生用と同じ暗証番号(`HOST_PIN`)を入力する。暗証番号はそのブラウザのタブを閉じるまで保持し、API 呼び出しのたびに `Authorization` ヘッダーで送る。サーバーは毎回検証し、違えば 401 を返す。
- 画面の構成: 左にセットの一覧、右に選んだセットの問題一覧(狭い画面では上下に並ぶ)。
- できること:
  - セット: 一覧(名前と問題数)、新規作成、名前の変更、削除(中の問題も一緒に消える。確認つき)。
  - 問題: 選んだセット内の一覧(問題文と正解)、追加・編集(問題文、選択肢4つ、正解をラジオボタンで1つ選ぶ)、削除(確認つき)。
- 入力の決まり: セット名は1〜30文字で、他のセットと同じ名前は不可。問題文は1〜200文字、選択肢は各1〜40文字、4つすべて必須、同じ問題内で選択肢の重複は不可、正解は必ず1つ。違反は保存せず、画面に日本語で理由を表示する。同じ検証をサーバー側でも行う。
- API(管理画面専用、JSON):
  - `GET /api/sets`(一覧)、`POST /api/sets`(作成)、`PUT /api/sets/:id`(名前変更)、`DELETE /api/sets/:id`(削除)
  - `GET /api/sets/:id/questions`(セット内の問題一覧)、`POST /api/sets/:id/questions`(追加)
  - `PUT /api/questions/:id`(更新)、`DELETE /api/questions/:id`(削除)

## 10. Flutter アプリの作り

- 追加パッケージ: `web_socket_channel`(通信)、`shared_preferences`(参加者IDと名前の保存)。
- 【提案】状態管理は Flutter 標準の `ChangeNotifier` を使い、外部の状態管理パッケージは入れない(画面数が少なく、状態はサーバーから届く1つのかたまりのため)。
- 層: 通信(接続・再接続・JSON の変換)/ ゲーム状態(サーバーから届いた `state` を保持し画面に通知)/ 画面。画面はフェーズに応じて切り替える(画面遷移の履歴は持たない)。
- 管理画面はこの Flutter アプリには含めない(サーバー側の HTML)。
- 見た目: Material 3。学校向けに明るく、文字とボタンを大きく。早押しボタンは画面で一番目立つ要素にする。配色や細部は作り手に任せる。

## 11. テスト

- サーバー: 純粋な状態機械を vitest で単体テストする。最低限、次を確認する。
  - 同じ出題フェーズで2人が押しても解答権は先着1人だけ。
  - 正解で +1点、結果フェーズへ。
  - 不正解でお休みになり出題に戻る。お休みの人は押せない。全員お休みで結果フェーズへ。
  - 受付時間切れ・解答時間切れの扱い。
  - 表示済み文字数の計算と、一時停止・再開。
  - 10問で最終結果になる。順位の同点処理。
  - 途中参加、再接続での得点復帰、名前の重複拒否。
  - 先生の操作(開始・中止・もう一度・全員退出・1人退出)と暗証番号の検証。
  - 問題の検証(文字数、選択肢の重複、正解の指定)、出題数がセットの問題数を超えないこと、選んだセットの問題だけが出ること、0問のセットや存在しないセットでは開始できないこと。
- サーバー(API): 暗証番号なし・違いで 401 になること、セットと問題の追加・更新・削除が一覧に反映されること、セットを消すと中の問題も消えること、セット名の重複拒否、初回だけサンプルセットが登録されること。
- Flutter: 通信メッセージの変換と、フェーズごとの画面表示(早押しボタンが出る/4択が本人にだけ出る など)をウィジェットテストで確認する。
- 通し確認: ローカルでサーバー(`wrangler dev`)を起動し、Android エミュレーターでアプリを動かす。早押しの相手役として、2台目のエミュレーターまたは Chrome / Windows 版を同時に起動し、先生役も含めて1ゲームを最後まで遊ぶ。管理画面で新しいセットを作って問題を登録し、先生画面でそのセットを選んで出題されることも確認する。

## 12. 公開

- 開発と動作確認は、開発機上の `wrangler dev` とエミュレーターだけで完結する(Cloudflare への公開なしで遊べる)。
- Cloudflare への公開手順: `server/` で `wrangler deploy`。初回は `wrangler login`(ブラウザで承認)と `wrangler secret put HOST_PIN` が必要。この2つは依頼者の操作が要る。その後、公開先の `wss://` アドレスを `SERVER_URL` に指定してアプリをビルドし直す。
- 公開先 URL は `*.workers.dev` の既定のものを使う。独自ドメインは対象外。
- 公開は外部に見える操作なので、実行前に依頼者に確認する。
- 【提案】作る順番は、ローカルで全機能を完成させてから最後に Cloudflare へ公開する。
